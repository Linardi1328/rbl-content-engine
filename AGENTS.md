## Shared evidence architecture

Keep three domains separate.

### Project evidence

Determines **what factual claims are allowed** about a project. Every factual project claim must trace to valid project evidence. The local ProofLab contract in `src/rbl_content_engine/prooflab.py` provides `VerifiedClaim` values and `require_verified_claims()` as the fail-closed factual boundary for future generation paths. No external ProofLab service is authorized by this milestone.

### Platform research

Determines **how verified facts may be packaged** for a target platform: audience intent, hook, format, pacing, story structure, visual treatment, and content archetype. It is a dated hypothesis set, not project evidence and not guaranteed market truth.

### Revenue & audience intelligence

Determines **which content opportunities are commercially worth testing and what was observed afterward**. It may use explicit human opportunity scores, monetization-route tags, dated research lineage, and manually exported first-party analytics. It must never become evidence for project facts or be described as proof of causality.

## Phase 0 boundary

Phase 0 remains the manual evidence-to-content pilot:

```text
project/GitHub evidence
-> claims with evidence references
-> deterministic claim verification

manual direction brief + dated local platform research
-> platform-specific strategy

verified claims + strategy
-> platform-native drafts/storyboards
-> verifier report
-> pending human approval
```

Phase 0 must remain fully offline. It does not publish content, message customers, call paid APIs/models, automate live trend research, automate video production, or auto-approve content.

## Phase 2A — Revenue & Audience Intelligence

Phase 2A is a separate offline module inside the same parent project. Follow `docs/revenue-intelligence/PHASE_2A_SPEC.md`.

Allowed Phase 2A flow:

```text
dated local platform/commercial research
+ explicit human-scored content opportunities with rationale for every factor
+ optional manually exported first-party analytics snapshot
-> deterministic opportunity ranking
-> monetization-route tags
-> audience + commercial hypothesis registry
-> fixed-window observation comparison
-> learning report
-> HUMAN DECISION
```

Phase 2A may:

- ingest local JSON opportunity manifests;
- score documented 0–5 factors using a fixed/versioned deterministic formula;
- require a non-empty rationale for every factor, including risk;
- tag intended monetization routes without claiming eligibility or revenue;
- declare one audience target and an optional commercial target per opportunity;
- require a fixed evaluation horizon before grading observations;
- ingest one manually exported cumulative analytics snapshot per content item;
- normalize documented aliases and ignore irrelevant columns;
- fail closed on duplicate content snapshots, platform mismatches, timestamp errors, or revenue-currency mismatches;
- generate deterministic JSON/Markdown ranking, hypothesis, and learning artifacts.

Phase 2A must not:

- browse the web or fetch live trends;
- connect to YouTube/Instagram/TikTok/commerce/CRM/payment APIs;
- publish or schedule content;
- send customer/lead messages;
- spend money or call paid models;
- infer causal relationships from observational analytics;
- auto-change strategy or approve content;
- use analytics/market data to support factual project claims;
- add a database, web service, queue, vector store, or agent framework.

Human-scored factors are explicit judgments, not measurements generated by the engine. Reports must describe scores and target outcomes as decision aids, not forecasts or causal proof.

## Non-negotiable factual rules

- Every factual project claim must trace to project evidence.
- Unsupported/conflicting factual claims must fail closed before future generation/production paths.
- Evidence references must remain attached through factual outputs.
- Platform strategy must retain snapshot/date/source lineage.
- Revenue intelligence must retain research snapshot/date lineage.
- Never claim or imply guaranteed views, reach, virality, sales, leads, or revenue.
- Human approval/decision remains required before publication or external action.
- Human direction may override strategy recommendations when factual/safety boundaries remain intact.
- No secrets, tokens, credentials, or `.env` values belong in tracked fixtures.

## Phase 3A — Provider-Neutral Production

The human owner has explicitly authorized Phase 3A after the Phase 2 completion boundary. Follow `docs/production/PHASE_3A_SPEC.md`.

RBL owns the production methodology; rendering providers are replaceable backends. Higgsfield, Topview, MuAPI, local inference, and future providers must not silently redefine SceneCards, factual lineage, locked references, continuity, QC, or approval gates.

Prototype progression is:

```text
PROVE_PIPELINE
-> PROVE_REPEATABILITY
-> STABILIZE_PROVIDER
-> HUMAN PROVIDER / SUBSCRIPTION DECISION
```

Provider stabilization is blocked until the versioned Phase 3A evidence gate is satisfied. Reaching the gate never automatically activates a subscription, trial, API spend, migration, or generation job.

Free/trial generations are tactical prototype capacity only. Do not architect RBL around a temporary allowance or assume a public/open-source client makes hosted inference free.

Never use shared, leaked, copied, repository-embedded, or third-party API credentials. Provider credentials and entitlements must belong to the human owner or an authorized workspace and remain outside tracked files.

Phase 3A code is read-only/planning-only: provider capabilities, cost quotes, prototype records, readiness evaluation, and human authorization guards. It intentionally exposes no generation submission method.

## Stage 3B–3E — Controlled Production Prototype

The human owner authorized implementation of the full Stage 3 engineering stack after Phase 3A. Follow the Phase 3B/3C/3D/3E production specs in order.

Stage 3 implementation may perform explicitly scoped live provider discovery and synthetic/public-safe prototype generation within the existing budget guardrails. It must still fail closed on provider/account-tier restrictions and must not claim an external generation succeeded unless a live job/output was actually observed.

Model discovery, cost estimation, and execution eligibility are separate facts. A catalog entry or successful cost quote does not prove that the active account can execute that model. Production preflight must positively establish model-level execution eligibility.

Automatic social publication remains prohibited. Phase 3D accepts only human-confirmed `MANUAL_EXTERNAL` publication receipts and matching first-party observation records. Never fabricate published content IDs, publication timestamps, or social metrics from a generated file.

Stage 3E may establish provider-stabilization readiness but must leave `provider_selection = HUMAN_DECISION_REQUIRED`. Reaching the stability gate does not automatically buy a Higgsfield plan, activate a trial, migrate providers, or create a paid API account.

## Topview production operator contract

Topview remains downstream of verified content and does not override Phase 0 or Phase 2A boundaries.

For Topview-related work:

- Codex acts as **RBL Topview Production Operator**, not factual verifier or creative authority.
- Read `docs/topview/WORKFLOW.md`, `docs/topview/TOOL_MAP.md`, `docs/topview/DISCOVERY.md`, and `docs/topview/PHASE_1D_PILOT.md` before executing the applicable Topview operation.
- Factual content must already pass `require_verified_claims()` before entering a Topview Production Manifest or future execution path.
- Treat human-approved references/keyframes as authoritative; locked assets must not be silently redesigned.
- Prefer approved-keyframe image-to-video for important shots where appropriate.
- Default controlled AI-generated clips to roughly **4–8 seconds**; longer shots need explicit justification.
- Use **720p** for draft motion/composition testing and only advance to **1080p** after the required QC/human gate when a later authorized live model supports those resolutions.
- Preserve entry/exit continuity and duplicate/identity/object-count QC constraints.
- Never guess Topview tool names, model IDs, permissions, remote asset IDs, or schemas. Public docs establish `OFFICIAL_DOC`; an active connected session establishes `VERIFIED_LIVE`.
- Record live discovery in `.production/topview-capabilities.json`; never commit that file.
- Phase 1 CLI intentionally **provides no paid-generation authorization switch**.
- Live capability/reference/state files remain local under `.production/` and must not be committed.
- Successful upload/registration never implies human approval.
- Reference locking binds source path/fingerprint, observed remote asset ID, and explicit human approval; **source drift after locking is a hard stop**.
- Record the live Phase 1D registry in `.production/topview-references.json`; never commit it.
- A validator or preflight result never authorizes spending.
- Authentication/Canvas ownership failures are hard stops.
- Approval is scoped; no intermediate approval implies final publication approval.

Current Phase 1 contracts and Phase 3A do not authorize chargeable generation. A later live production milestone requires a new explicit human authorization before any provider submits a billable generation.

## Engineering defaults

- Python 3.11+.
- Prefer the standard library; add dependencies only for a concrete requirement the standard library cannot reasonably satisfy.
- Prefer plain files and explicit data structures over services or orchestration systems.
- Keep deterministic logic deterministic: stable ordering, filenames, formatting, scoring, and reports.
- Use tests for verification, scoring, import normalization, and report generation.
- Synthetic/public-safe fixtures only in tracked demos.
- Generated artifacts should be human-inspectable without special tooling.
- Treat platform/revenue profiles as dated decision inputs, not timeless truths.

## Phase 0 definition of done

A local command can run one synthetic/public-safe fixture end-to-end and produce evidence/claims, platform strategy, platform-native treatments, verifier report, short-form storyboards, and `PENDING_HUMAN` approval status without network access.

## Phase 2A definition of done

A checked-in synthetic/public-safe example can:

1. rank several content opportunities with a documented/versioned deterministic score;
2. show a non-empty rationale for every scored factor;
3. retain explicit monetization-route intent;
4. produce separate audience and commercial hypotheses;
5. define a fixed observation horizon;
6. optionally ingest one cumulative manually exported analytics snapshot per content item;
7. reject duplicate snapshots and cross-platform/currency mismatches rather than guess;
8. grade audience and commercial targets separately only after the window matures;
9. produce deterministic JSON and Markdown learning artifacts;
10. run fully offline with no credentials or external side effects;
11. pass `make check` and `make test` across the supported Python matrix;
12. leave the Phase 0 factual-verification and human-approval boundaries intact.

Stop Phase 2A there. Live analytics APIs, scheduled research, dashboards, databases, publishing, customer messaging, paid generation, and autonomous strategy changes require later explicit milestones.
